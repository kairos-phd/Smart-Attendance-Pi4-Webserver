# Web Application & Wireless Communication

## 1. Purpose

The Web Application provides the user interface for monitoring,
managing, and interacting with the Smart Attendance System.

The wireless communication layer allows Raspberry Pi devices,
cameras, cloud services, and client devices to communicate without
requiring a direct physical connection to the user's computer.

The design should prioritize reliability, simplicity, low cost,
security, and compatibility with the available hardware.

---

## 2. System Communication Architecture

Current proposed architecture:

Camera
    ↓
Raspberry Pi 4
    ↓
WiFi / Ethernet
    ↓
Internet / Local Network
    ↓
Firebase / Backend
    ↓
Web Application
    ↓
User Device

The Raspberry Pi acts as the edge device.

The user's PC, laptop, tablet, or smartphone acts as the client.

The client should not need to connect directly to the Raspberry Pi
unless required for administration or local deployment.

---

## 3. Wireless Connectivity

Primary connection:

WiFi

Alternative:

Gigabit Ethernet

The system should support operation over a local network when
possible.

Internet/cloud connectivity should be used when remote access,
cloud synchronization, or external monitoring is required.

The system should be designed so that temporary Internet loss does
not immediately cause loss of attendance data.

---

## 4. Raspberry Pi Communication

The Raspberry Pi is responsible for:

- Camera management
- Motion detection
- Image capture
- Face detection
- Face recognition
- Attendance processing
- Communication with the backend/cloud
- Device status reporting

Possible communication technologies:

- HTTP/REST
- WebSocket
- MQTT
- Firebase SDK
- Local TCP/IP

The final communication protocol should be selected according to
actual system requirements rather than using every technology.

---

## 5. Web Application

The Web Application should allow administrators or authorized users
to:

### Attendance

- View current attendance
- View attendance history
- Search attendance records
- Filter by date
- Filter by user
- Filter by camera/location

### User Management

- Register users
- Update user information
- Delete users
- Register/update face data
- View user attendance history

### Camera / Device Management

- View camera status
- View Raspberry Pi status
- Identify camera location
- Detect disconnected cameras
- View device connection status

### Unknown Faces

- View unknown-face events
- View captured images
- View timestamp
- View camera/location
- Optionally associate an unknown face with a registered user

### Statistics

- Daily attendance
- Weekly attendance
- Monthly attendance
- Attendance percentage
- Late/absent statistics

### System Monitoring

- Raspberry Pi online/offline
- Camera online/offline
- Last synchronization time
- System errors

---

## 6. Client Devices

The Web Application should preferably support:

- Desktop
- Laptop
- Tablet
- Smartphone

The interface should be responsive.

Users should be able to access the system through a normal web
browser without installing dedicated software.

---

## 7. Local vs Remote Access

### Local Network

Example:

Raspberry Pi
    ↓
WiFi Router
    ↓
Laptop / Smartphone

This allows the system to work without Internet access for local
demonstration and testing.

### Remote Access

Example:

Raspberry Pi
    ↓
Internet
    ↓
Firebase / Backend
    ↓
Web Application
    ↓
User anywhere

Remote access should only be implemented if it is useful to the
project and can be achieved without unnecessary complexity or cost.

---

## 8. Offline Operation

The system should consider temporary network failure.

Recommended behavior:

Camera
    ↓
Raspberry Pi
    ↓
Attendance detected
    ↓
Local temporary storage
    ↓
Internet unavailable
    ↓
Store locally
    ↓
Internet restored
    ↓
Synchronize with cloud
    ↓
Firebase

This prevents attendance records from being lost because of a
temporary WiFi or Internet failure.

---

## 9. Security

The system should consider:

- User authentication
- Authorization
- Secure communication
- Firebase security rules
- Protection of face data
- Protection of attendance records
- Secure WiFi
- Raspberry Pi access control
- SSH security

Face recognition data should not be exposed unnecessarily to
clients.

---

## 10. Recommended Technology Candidates

Frontend:

- ReactJS
- HTML/CSS/JavaScript

Backend:

- FastAPI
- Flask
- Firebase SDK

Communication:

- HTTP/REST
- WebSocket
- MQTT
- Firebase SDK

Cloud:

- Firebase Firestore
- Firebase Storage
- Firebase Authentication

The final technologies should be selected based on:

- Raspberry Pi 4 capability
- Development complexity
- Team experience
- Cost
- Required real-time performance
- Security
- Scalability

Do not introduce a separate backend, MQTT broker, WebSocket server,
and Firebase unless the project actually benefits from them.

---

## 11. Application Architecture

The system should preferably follow:

Device Layer
    ↓
Edge Processing Layer
    ↓
Communication Layer
    ↓
Cloud / Backend Layer
    ↓
Application Layer

For this project:

Camera
    ↓
Raspberry Pi 4
    ↓
WiFi
    ↓
Firebase / Backend
    ↓
Web Application

---

## 12. Future Expansion

The architecture should allow future support for:

- Multiple Raspberry Pis
- Multiple classrooms
- Multiple locations
- More cameras
- Mobile application
- Push notifications
- Real-time WebSocket updates
- MQTT-based device management
- Centralized device management
- Remote configuration
- Cloud-based analytics

These features are considered optional extensions and should not be
implemented unless they are necessary or achievable within the
project timeline.
